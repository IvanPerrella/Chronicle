# Enhanced lighting plan

The target is `Dark Cloud_ Gunny in the Fog.png`: cool teal atmospheric haze, localized warm lantern light, restrained glow, dark contact regions and rough wet-floor highlights, with legible HUD. Preserve the original renderer as an option. At the start of this work the port drew into RGBA8 Vulkan targets, computed Lambert lighting per mesh vertex, carried material specular without using it, and had no motion-vector, acceleration-structure or postprocess pipeline. Its 2D overlays, frame feedback and GS blend emulation depend on the current color path.

## Integration sequence

1. **Materials and fog.** Add opt-in per-fragment dielectric specular with explicit roughness and proper camera/world inputs. Prefer asset-specific material overrides for wet wood and rough walls to a global gloss boost. Apply atmospheric fog to world geometry with a cool medium; keep 2D and HUD clear. Retain the original GS shading when disabled.
2. **Scene postprocessing.** Draw the enhanced world into linear RGBA16F, apply a bright-pass, low-resolution blur and restrained bloom, then tone-map into an SDR target before compositing the HUD. Keep the canonical image used by the game's own frame grabs free of presentation-only effects.
3. **Ray-traced scene.** Make Vulkan acceleration structures, buffer device address and ray query optional device capabilities. Cache BLAS for static meshes, update dynamic geometry, and build a TLAS for each displayed scene. Account for geometry beyond the visible raster draw list when tracing reflections, shadows and GI. Respect alpha-tested surfaces; skip UI and synthetic shadow-volume draws.
4. **Ray effects.** Begin with short-range AO and selected warm-light shadow rays, then roughness-aware reflections, then diffuse GI with temporal history or probes. Each effect needs denoising and history rejection. NVIDIA NRD's Vulkan sample illustrates the normal, roughness, depth and motion guides required. RTXGI's DDGI integration is an option once the RT scene is complete.
5. **Temporal rendering.** Supply stable camera and object identifiers, previous *displayed* transforms, deformed-vertex motion and dense motion vectors. Track cuts, teleports, resize and skipped presentation. Split 3D scene from HUD so temporal reconstruction and Frame Generation get HUDless color and a separately composited UI.
6. **DLSS Super Resolution and Frame Generation.** Integrate the current Streamline Vulkan path with explicit SDK capability queries, device/present hooks, frame tokens, jitter, depth, motion, exposure, Reflex and correctly declared reverse-Z/matrix conventions. Keep a native-resolution fallback. Frame Generation is supported on Vulkan in the current Streamline programming guide; use SDK-reported support instead of a GPU-name check. Never report either feature enabled until Streamline evaluates actual frames.

The NVIDIA DLSS page currently describes DLSS 4.5, its second-generation transformer Super Resolution model, and Dynamic/6× Multi Frame Generation. These release names describe SDK capability; the port still has to query the installed Streamline plugins and prove each active mode on the user's GPU. The October 2026 Streamline 2.14.1 Frame Generation guide includes Vulkan integration and Reflex requirements.

## Streamline implementation status (October 2026)

The optional Windows Vulkan build loads NVIDIA-signed Streamline 2.14.1 plugins, queries DLSS Super Resolution, Frame Generation and Reflex support, and uses the SDK's Vulkan swapchain/present hooks. DLSS receives the HDR world before HUD composition, depth, dense camera motion with opaque-mesh overrides, frame tokens, projection jitter, and reset signals after cuts or target changes. Quality, Balanced and Performance use SDK-selected reduced world sizes; DLAA renders at output size. The renderer composites the HUD after reconstruction and keeps its native path available when DLSS is off or unavailable.

Frame Generation receives a per-frame HUDless SDR world image, depth and motion, with Reflex markers. It is opt-in and requires SDK support plus an Immediate-present-capable swapchain; enabling it selects Immediate without rewriting the saved V-Sync choice, and disabling it recreates the swapchain in the saved mode. The current integration requests one generated frame per rendered frame, not NVIDIA's newer multi-frame modes. SDK support alone is not considered activation: `numFramesActuallyPresented` is checked after real presents. In a current Release RTX 4090 Shipwreck test at 3840×2160 output and 2560×1440 Quality input, the game window gained foreground focus and Streamline reported `latest=2 status=0x0`; totals were 1,186 real, 1,293 SDK-presented and 107 generated frames (`.kazarov/fg-same-shell.log`). Those totals include preceding unfocused frames, so they do not imply a 2× rate across the whole run. A separate unfocused Release test reported one shown frame per real frame and zero generated, despite successful SR and FG setup. SDK counts are not a physical-display pacing measurement.

Graphics settings now queue changes until a frame boundary. The renderer rebuilds world targets before either a canonical draw or an interpolated display replay, resets temporal history when DLSS size or HDR mode changes, and recreates the swapchain when Frame Generation changes. A Shipwreck integration run exercised HDR, ray queries, Performance→DLAA→Quality, Frame Generation on/off, bloom, fog, local lights, and DLSS Off→Quality during play without a Vulkan or NGX error. The Frame Generation disable transition logged restoration of the saved FIFO swapchain mode. Remaining temporal limits are moving translucent/2D depth sprites and any deformation not matched by the mesh history; camera reprojection covers the background, while only eligible opaque depth-writing meshes write object motion. A driver-generated frame is presented by Streamline rather than captured by the port's screenshot path, so visual QA of generated-frame artifacts requires display capture or direct observation.

Consecutive 4K Shipwreck display readbacks at game frames 850–851 used scripted character movement and camera rotation with Frame Generation both off and on. All four runs evaluated reduced-resolution DLSS, and the app-rendered images showed stable character and floor edges with the HUD remaining sharp; they did not expose an obvious trail in that short sequence. Earlier Frame Generation-on runs separately reported generated presentations through the SDK, but screenshots show application frames, not generated intermediates. This limited capture cannot establish generated-frame artifact quality during longer or faster motion.

The live Surface Detail setting controls the material-specific procedural normal maps in `assets/materials`. The distributed pack has normal and ORM PNGs for wet floor timber, wall timber, cloth, leather, skin, metal, stone, generic props and flat surfaces; the normal maps are original approximations generated by `tools/materials/generate_material_maps.py`, not artist-authored scans. The renderer keeps the game's authored UVs where present and uses stable world projection for untextured props. Toan's face, leather accessories and cloth atlases select their matching profiles, while a mixed atlas stays conservatively cloth with a smooth-skin mask. UI and shadow meshes do not receive bump detail. Prefiltered mip levels reduce high-frequency shimmer at distance.

Shipwreck's fullscreen fog integrates background extinction and a thin lower blue-green medium along each camera-to-depth ray before the HUD is drawn. The fog uses a stable 20×20 collision-derived deck-height field tied to the dungeon layout, with blended cell boundaries and a fixed fallback while collision data loads. This replaced the player-ground-height estimate, which moved the entire fog volume when Toan crossed between floor elevations. A regular gameplay traversal from the lower room into its south corridor confirmed continuous haze and geometry across the actual room switch; see the follow-up evidence in ENHANCED_LIGHTING_STATUS.md.
